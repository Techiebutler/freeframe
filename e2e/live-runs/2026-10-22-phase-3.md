## Deviations from the brief and the protocol

1. **Clipboard path replaced** (as in phase 2): `navigator.clipboard.readText()` hangs in a fresh isolated context, so the password reached the form
   through a mode-0600 file in `e2e/.live-files/` uploaded to an injected file input and read in the page; the file was deleted at once and
   the clipboard cleared. The password was never in a tool call or in this report.
2. **Laptop sleep was not run** (controller ruling R9: the Mac must not be put to sleep). Recorded as: **laptop sleep: moved to the manual pass.**
3. **"Touch a file in a synced folder" used a plain local folder.** This machine has Google Drive, OneDrive and iCloud Drive folders, but none
   is a test location, so none was touched. The files sit in `e2e/.live-files/` and X3 does what a sync client does to a file
   (rewrite in place, replace by rename, touch).
4. **Stand-ins for the Playwright faults** (`e2e/live-tools/`, `LIVE-CHROME.md` section 9). The DevTools MCP cannot hold or answer a request, so:
   - `hold()` / `release()` stop a part PUT at `XMLHttpRequest.send` (U1, U2, U3, N2, X3). **A held part is not a hung socket**: nothing
     reaches the network, and the app's watchdog still runs on it because it armed the clock when it called `send`. An abort of a held part
     ends the way the browser would end it (`abort`, `loadend`). This is `hangParts` / `holdParts`.
   - **Real sockets where progress mattered** (U3b, U3c, X2b): a throwaway server on `127.0.0.1:18777` (`live-tools/stall-server.js`, new in this
     pass, outside the stack) and an in-page `XMLHttpRequest.open` redirect (`live-tools/ffq-route.js`, new). `/stall` reads about 256 KB of a
     part and stops reading, so Chrome reports real upload progress (1 081 344 and 1 097 728 bytes in two progress events) and then nothing:
     `stallParts`. `/hang` reads the whole body and never answers. The redirect keeps the query string, so the probe still counts the PUT.
     U3b and X2b used an earlier inline form of the same redirect (`q.stallNext`); the saved `ffq-route.js` is the form U3c ran. Chrome lists
     the redirected PUT as `127.0.0.1:18777/stall?...` (`net::ERR_ABORTED` once the watchdog ended it).
   - `emulate` presets only: `Offline`, `Fast 4G` (168 750 B/s up), and a bare `emulate` for online.
5. **The outages were longer than written** because the tool calls between "offline" and "online" take seconds: N1 32.5 s (written 30), N2
   27.7 s (written 20), X2 164 s and X2b 125 s (written 120). The times below come from the page's own `offline` / `online` events.
6. **Console**: read at the end for the whole document (SPA navigation never reloaded it), see "Console". No `window.onerror` trap was installed;
   an uncaught error would have been listed as an `[error]` line, and there is none.
7. `gif_creator` was not used: no scenario failed. The DevTools network list is a rolling window; counts below are the probe's, and where the
   list was read for a scenario it is quoted next to them.
8. Screenshots are in `<scratch>/live-p3/shots/`, where `<scratch>` is the working session's scratch directory; none is committed.

## Observations for the controller (no scenario failed because of these)
1. **No app bug found in U1, U2, U3, N1, N2.** `apps/` was not touched.
2. **After a reconnect the app waits out its backoff instead of waking on the browser's `online` event.** N1 took 29.6 s from the network returning to the first retry (the 62.1 s try), X2b 22 s for the queued files and 26 s for the big file's rung. Inside the spec ("all complete after reconnect") and the 60 s cap, so not a failure; an `online` listener that wakes the hold and the ladder would remove the idle gap. Worth a ticket, not a fix in this phase.
3. **An outage that lands on `/upload/complete` ends the row Interrupted with the raw browser text "Failed to fetch"** (X2), where an outage on a part is retried for minutes (X2b, N2). The data is whole and Resume finishes it without sending a byte, so nothing is lost, but the copy is the browser's and there is no automatic retry of the complete call. It predates the queue and the phase 3 expectation ("Interrupted as today") covers it; flagging it because "Waiting for connection" is what a user would expect here.
4. **A file deleted after its last part started is uploaded anyway** (X1, macOS), and one with a part still to start fails at that part (X1b, U2). Both are consistent with "the file is read when its bytes are needed"; the first means a successful upload from a file that no longer exists on disk. Nothing to fix; stating the behaviour.
5. The retry of an aborted part waits for a budget slot like any other attempt, so while one file holds all five slots a stalled file's retry can wait for the next freed slot (U3c: c's retry went 24.7 s after its abort, a's 19.4 s after its abort, the throttle being lifted in between). Expected from the budget design.
