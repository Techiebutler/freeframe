`live-runs/2026-10-21-baseline.md`. Every scenario of the phase was run by hand in a real, headed Chrome,
plus the exploratory checks from the task brief.

## Deviations from the brief and the protocol

1. **No custom 2 MB/s (Q1).** Same as the baseline: the DevTools MCP only has presets. Q1 ran at **Fast 4G**
   (168 750 B/s up, 165 ms) from before the drop, sampled at about +5, +20, +30, +100 and +158 s, and the throttle was
   **lifted at +158.4 to +161.8 s** (the last probe read before and the first after; the lift was between them) to
   reach an end state. Nothing was cancelled.
2. **Clipboard path replaced.** `navigator.clipboard.readText()` in a fresh isolated context asks for a permission
   that the MCP cannot grant (the call hangs, "prompt"), so the password reached the form through a mode-0600 file
   uploaded to an injected `<input type=file>` and read with `FileReader` (deleted at once). Neither the password nor the
   file content was ever in a tool call. `LIVE-CHROME.md` section 2.2 says so now.
3. **Stand-ins for the Playwright faults** (`e2e/live-tools/`, `LIVE-CHROME.md` section 9). The DevTools MCP cannot hold,
   delay or answer a request, so the in-page probe got: `hold()`/`release()` for part PUTs (`holdParts`),
   `pace(bytesPerSecond)` (`throttleParts`), `delayInitiateMs`, `failInitiate = n` (the API's coded 503, `retry_after` 5),
   a stand-in file chooser for Resume, `delayPartsMs` (a deferred `/parts` answer, as R3's route does), and logs of every
   initiate (name, status, answer), part PUT (upload id, size) and presign. A held part PUT that the app aborts ends as the
   browser would end it (`abort` and `loadend` events). **The probe's own `block()` stands in for request blocking**
   (E2, S2): S2's PUTs failed as network errors, not as HTTP 503. S1 used the **real fault** instead:
   `docker stop ffe2e-minio-1` (container of the e2e stack only), then `docker start`.
4. **A 2 s gap is made by script.** Q3 was run twice: a first time with the two `upload_file` calls in between
   (16.9 s apart), then with two pre-loaded inputs and both drops in one script, **2 003 ms apart** (the verdict).
5. **Interrupted uploads are made by reloading the page** (R1, R3, E3): `navigate_page` `reload` keeps the tab's
   `sessionStorage`, so the rows read Interrupted (a closed and reopened page would read Elsewhere for 150 s, as the
   Playwright R1 notes). Each such page was then re-instrumented from `e2e/live-tools/`.
6. **The DevTools network list is a rolling window across the session** (SPA navigation does not clear it): for Q1 the
   `xhr` filter showed 52, then 50, PUTs where the probe counted 62 (the oldest dropped out between two reads), so the
   probe is the authoritative count; C1's last page (read right after the run) agrees with the probe count for count.
   Read the last page (`pageIdx`) to see a scenario's own requests.
7. **Console**: read at Q1 (clean) and once over the last three documents at the end (see "Console"); the earlier
   documents' consoles were not captured, and no `window.onerror` trap was installed, so "no uncaught error" for the
   scenarios in between rests on the app having behaved (no row failed unexpectedly and no scenario stalled).
8. The panel lists the account's earlier uploads (the Playwright suite's rows, history), so rows were found by name
   prefix; the "Interrupted" and "Cancelled" rows sit in the panel's **Failed** tab, not Active.
9. `gif_creator` was not used: the one failure (APP-BUG-1) is reproduced by an automated test whose trace and
   screenshot are linked below.

## R1 Interrupt, reopen, Resume while files are queued: FAIL (APP-BUG-1)
- Expectation: "the Resume starts next; its `ff-uploads` entry exists throughout".
- Result, literal part: PASS. Project `Live P2 R1`: a 12 MiB file (two parts, held so no byte left) saved with its version and upload ids, the page reloaded (the row came back Interrupted, saved `interrupted`), 13 files dropped (3 Uploading, 10 queued), Resume picked through the **real file chooser**: "Waiting to resume" (`interrupted / waiting-to-resume`), no `/parts` call before its turn. After the release, `GET /upload/<version>/parts` went at +18 140 ms, **33 ms before the fourth file's initiate** (+18 173 ms): the Resume starts next. 145 writes of `ff-uploads`, 0 without the row, statuses `interrupted` then `elsewhere`.
- Result, actual outcome: **the Resume did not resume.** After the answer the row turned `elsewhere` ("Still uploading in another tab or on another device"), no part was presigned or sent for it, and, by the code's own comments (`elsewhere` offers no Resume and no Discard), nothing to click for about 2 minutes (the saved status stayed `elsewhere` for ~120 s, then went `interrupted` again). The 13 files finished normally.
- Cause (read from `stores/upload-store.ts`): `activeElsewhere()` keeps the user's control of their own upload for `OWN_STOP_GRACE_MS` = 30 s, measured from the row's last `heartbeatAt`; after that, an upload whose server `last_activity_at` is younger than `LIVE_WINDOW_MS` (150 s) counts as running in another tab and the Resume is refused. Nothing refreshes `heartbeatAt` while a Resume waits in the queue, so a Resume clicked inside the grace but started after it is refused when its turn comes. The Playwright R1 never sees it because its Resume starts within seconds of the page closing.
- Controlled reproduction (R1b, project `Live P2 R1b fast resume`): same shape, driven fast so the click fell inside the grace: Resume clicked **20.5 s** after the last heartbeat, 8 files queued, parts held 15 s more; the Resume started at heartbeat age **41.6 s**: `GET /parts` 200, row `elsewhere`, 0 part PUTs for it. **Control (R1c)**: the same Resume with no queue, clicked at heartbeat age 12 s, started at once: `/parts` 200, 2 presigns, 2 part PUTs, `complete` 200, the row went Processing. So the queue's wait is what turns a good Resume into "Elsewhere". E3 (below) is the same flow with the Resume starting inside the grace: it works.
- Automated reproduction (committed, marked `test.fail()`): `tests/queue.spec.ts` "R1b: a Resume that waits in the queue past the own-stop grace still resumes". Without the marker it fails on Chromium: `Timed out after 60000 ms waiting for everything uploaded. Rows: r1b-...-01:elsewhere/elsewhere  r1bq-...:complete x8`; with the marker it passes (drawn as a cross) on Chromium and WebKit. Its failure screenshot: `<scratch>/live-p2/app-bug-1-elsewhere.png`. The fix's author removes the marker.
- Suggested fix direction (not applied, `apps/` untouched): a Resume that waits in the queue is this tab's own, so it should not be read as another tab's (keep `heartbeatAt` fresh while `queuedResume` waits, or exempt a row whose Resume this tab queued); plus a vitest in `upload-queue-resume.test.ts` that holds the slot for more than 30 s of fake time.
- Related, pre-existing and not queue-specific: a person who reloads and clicks Resume more than 30 s later hits the same refusal for up to 150 s of server inactivity.
