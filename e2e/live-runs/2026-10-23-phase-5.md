## Deviations from the brief and the protocol

1. **The chrome-devtools MCP could not start its browser**: its profile was held by the same Chrome as in phase 4 (pid 53237,
   parent `chrome-devtools-mcp` pid 77876, started 2026-10-21), another session's. It was left alone. Fallback, as section 10
   says: real Google Chrome, headed, with its own profile, `--remote-debugging-port=9333`, driven by `live-tools/cdp-driver.js`
   (Playwright 1.59 `connectOverCDP`). New in the driver for this pass: `init` (a script on every new document, before the
   app), `focus`, `bounds`, `reload {nowait}`, `close {runBeforeUnload}`, and `dialogs {answer, delayMs}` (how and when that
   page's dialogs are answered).
2. **Visibility through the driver is emulated, and could not be switched off from a second session.** Playwright turns
   focus emulation on for every page it attaches to. `Emulation.setFocusEmulationEnabled(false)` sent on the driver's own,
   second CDP session made `document.hasFocus()` false but left `visibilityState` "visible" with another tab in front
   (`Target.createTarget` and then `Page.bringToFront` on it: tab A still "visible", wake lock still held). So **V (visibility)
   was run with the driver stopped**, over a plain DevTools-protocol connection with nothing of Playwright's attached (new:
   `live-tools/cdp-raw.js`): a real foreground tab opened in the same window (`Target.createTarget`) and a real tab switch back
   (`Target.activateTarget`). The window was never minimized. Every other step ran through the driver with every page
   reading "visible" (W4's background tab included).
3. **Stand-ins** (`LIVE-CHROME.md` section 9): `hold()` kept part PUTs unsent (L1, the closed tab, L2, L3, L3b, W4);
   `pace(100000)` delayed each part by its size over 100 000 B/s (V; the throttle could not be used there, it is held by the
   driver, which was stopped); `failInitiate = n` answered `/upload/initiate` in the page with the API's coded 503 (W2, W2b;
   those refusals never reached the network); Offline was the driver's `Network.emulateNetworkConditions` (W3); the forced
   session end removed or spoiled the tokens in the page itself.
4. **The browser's `beforeunload` dialog was answered by the driver**, through the DevTools protocol (Playwright's
   `dialog.accept()` / `dismiss()`, so `Page.handleJavaScriptDialog`), after a delay of 1.5 to 3 s during which the dialog was
   up and the page blocked; not by a person's click. Evidence that it was the browser's own modal: Chrome reported
   `Page.javascriptDialogOpening` of type `beforeunload`, and an `evaluate` sent to the page while it was up timed out (the
   renderer was held by the dialog). Its on-screen look was **not captured**: `screencapture -R` failed ("could not create
   image from rect"; the terminal has no Screen Recording permission), and a Playwright screenshot cannot be taken while the
   page is blocked.
5. **The tab was closed with `page.close({ runBeforeUnload: true })`** (the DevTools protocol's `Page.close`, which runs the
   page's `beforeunload` as a person's close does), not with the tab's close button or Cmd+W, which the protocol cannot press.
6. **Tooling slip in the closed-tab run**: a click meant for the panel's **All** tab used `button:has-text("All")`, which
   matches **"Cancel all queued"** (a case-insensitive substring), and cancelled that run's two queued rows at about +3 s (C2
   behaving as designed). The first close was therefore made with 3 sending and none queued; the two files were dropped again
   at +39.3 s and the close repeated with 3 sending and 2 queued. New trap in `LIVE-CHROME.md`.
7. **Console not read for the first driver session and for V**: the driver's records end with it, and it was stopped for V
   (the plain connection keeps no console). So W1 and the L1 negative (first session) and V have no console reading. Every
   later step was read (see Console).
8. **DevTools-list counts** (the driver's network list) are given for W2 to W4 and L1 to L3; W1, V and the L1 negative have the
   probe's counts only, for the same reason as 7.
9. **The wake lock was observed from outside the app**: `live-tools/ffq-wakelock.js` (new), installed with the driver's
   `init` before the app runs, wraps `WakeLock.prototype.request` and logs each request, grant, refusal, `release()` call and
   browser `release` event with the page's visibility, mirrored to sessionStorage so a document's last entries survive a reload
   or the move to /login. As corroboration from the OS, a read-only sampler logged `pmset -g assertions` for this Chrome's pid
   once a second: Chrome holds a `NoDisplaySleepAssertion` named **"Blink Wake Lock"** exactly while a screen wake lock is held
   (a screenshot shows up as one named "Capturing"; ignore it). The store's `__uploadQueueTesting.wakeLockWanted()` was not used.
10. **Credentials**: the password and email of `primary` and `secondary` were in four mode-0600 files in `e2e/.live-files/pw/`
    for the pass (about 25 minutes) and deleted at the end; both were read inside the page, never in a tool call.

## Observations for the controller (no scenario failed because of these)
1. **A hold costs one short lock per probe try.** A try is `starting`, so each one takes the lock and gives it back when the
   answer comes: 3 to 11 ms here, where the refusal was answered in the page or offline. Against a real storage outage
   (phase 2: a coded 503 in about 150 ms) that is about 150 ms of lock every 5 s, and nothing between. As designed ("a hold
   lets the machine sleep"), and harmless; recorded so nobody mistakes the request/release pairs in a log for a leak.
2. **Leaving the page in the tab that ends the session does not release the lock first**: Log out, a forced end and a Leave
   all reach `pagehide` with the lock held, and the browser drops it with the document (the OS assertion was gone within
   about a second). The app's own release on sign-out is for a sign-out in another tab (W4), which it does at once.
3. **The queue does not wake on the browser's `online` event** (phase 3, Observation 2): 29.8 s from the network's return to
   the next try in W3.
4. **Own-tab Log out and Leave lose the never-started rows**: after L2's Log out and L1's Leave only the three that had
   started came back (Interrupted). The confirmation counted all five ("5 uploads will stop"), so the copy is right; the
   design does not keep queued files across a page load.
5. **When the owner signs back in before a held run resumes, the run finishes** (W4: the three completed as primary); in
   phase 4's A1, where the parts went while nobody was signed in, the run stopped Interrupted. Both match the store's rules;
   W4 is the first live run of the "back in time" order.
